# Generated artifacts

## The pattern

```text
+---------------------+     +--------------+     +--------------------------+
| source (hand-edited)|---->| generator    |---->| generated file           |
| YAML, JSON, TOML,   |     | one command  |     | banner: GENERATED from   |
| parts with includes |     | deterministic|     | <source> by <command>;   |
+---------------------+     +--------------+     | do not edit              |
                                                 +--------------------------+
                   drift check: render to memory, compare bytes, fail on difference
```

| Rule | Why |
| --- | --- |
| Find the true source before editing anything that looks generated; edit the source, never the output | A hand edit to output is lost at the next render |
| The generated file carries a banner naming its source and the command that renders it | The next reader knows not to edit it |
| The generator is deterministic: sorted keys, stable ordering, no timestamps in output unless the source holds them | Drift checks need stable bytes |
| A check renders to memory and compares with the committed file; a difference fails | Output cannot drift from source unnoticed |
| Render once, after all source edits, before the closing check | Repeated renders between edits waste time and hide which edit changed what |
| A large source is split into parts with an include list; the generator assembles them | One small file per concern is easier to change |
| A drawing, guide or catalog that has a data source is rendered from it, never drawn or written by hand | Data can be checked; a drawing cannot (a governed project: flows and team guides are data first) |

> **Learned 2026-11-12** · a second, easier-to-read format of a data file (JSON source, YAML view) · VERIFIED_PRIMARY (apn enterprise-strategy 64a64b0c: the view is

```python

```

## When the user has hand-edited a generated file

Preserve the user's hand edits: patch or append only, never regenerate over them; keep a backup and say what you touched (operator lesson
`feedback_preserve_user_hand_edits`). Then move the change into the source so the next render keeps it.

## Lock files

A lock file (dependency lock, image digest list) is generated by its tool and committed. It is changed only by the tool's own update command, and reviewed as a
diff. Why: a hand-edited lock file can claim a version the resolver never chose.

> **Learned 2026-10-21** · generated pages that depend on the clock · VERIFIED_PRIMARY (a drift check comparing a page with a render for today would have refused the first commit of every day; proved after the change with a page rendered as of the day before) · Source: unified-network-controller `scripts/render/plan_timeline.py`, `scripts/govcheck/checks/trackers.py` and its justfile `commit-gate` (2026-10-21) · Falsifier: a project whose commit gate cannot run a renderer (then the check must fail and a person renders)
> A generated block whose content follows today's date (late or due marks, day counts) goes stale every midnight without any edit. Do not
> make its drift check fail on that: every gated commit, in every session, would be refused until someone renders. Render in the commit
> gate before the check, so each commit carries a current page, and let the check fail only on bad data and print a note when the page
> merely trails today:
>
> ```text
> commit-project --apply -> check-cmd "just commit-gate"
> commit-gate: plan_timeline.py --write   (docs only, idempotent)
>              just check                 (bad data fails; "trails today" is a note)
> ```

> **Learned 2026-10-23** · generated spreadsheets, macOS review · VERIFIED_PRIMARY (observed) · Source: enterprise-strategy `scripts/weekly_update_xlsx.py` (uncommitted at the time; first commit after apn HEAD aec1db9) · Falsifier: a `qlmanage -t` thumbnail of a multi-sheet workbook that shows a later sheet, or an empty row without a set height
> Reviewing a generated .xlsx with Quick Look (`qlmanage -t -s <px> -o <dir> file.xlsx`) shows only the **first sheet** and **collapses empty rows**,
> so a spacer row looks missing although it is in the file. Review each sheet from a scratch copy with that sheet moved first (and rows above the
> area hidden), never by reordering the real output; and give spacer rows an explicit height so every viewer keeps them. Assert the layout in an
> offline test as well (cell values, fills, borders), because the thumbnail is evidence of the look, not of the content.
>
> ```python
> # scripts/weekly_update_xlsx.py: spacer rows get a fixed height so viewers that collapse empty rows still show them
> for note in notes:
>     plan.append([])
>     plan.row_dimensions[plan.max_row + 1].height = 15
>     plan.append(list(note))
> # review copy, not the output: move the sheet first, then `qlmanage -t` the copy
> wb.move_sheet("Plan and status", -1); wb.active = 0; wb.save(scratch / "preview.xlsx")
> ```

> **Learned 2026-10-23 (b)** · XML banners on generated files · VERIFIED_PRIMARY · Source: skill-drawio `scripts/drawio/mxfile.py:banner` (612d33e); draw.io 32.5.5 "Export failed" on every page · Falsifier: an XML parser that accepts `--` inside a comment
> A "generated, do not edit" banner written as an XML comment must not contain `--`: a regenerate command such as `render.py --write` in it makes
> the whole file not well-formed, and consumers refuse it with an unrelated error. Validate the banner text when it is built (raise), and name a
> task-runner recipe in the banner instead of a command with long options.
